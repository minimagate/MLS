# MLS — Math Language Server

The repository implements a testable v1 across M1–M5: a deterministic parser
CLI for TeXmacs native (`.tm`) documents, batch statement formalization,
human review, a persistent live daemon and plugin, and a proof core for
human-confirmed statements. The TeXmacs GUI still needs an owner visual pass.
The M1 parser finds sections, definitions, theorem-family
environments, equations, and proofs; reports exact-source hashes, labels, and
explicit label dependencies as JSON; and assigns unique UUIDs for the run.
Untagged rendered content in the document body is grouped into commentary blocks,
including its inline formatting and references. Preamble and control arguments
are never treated as prose; a native document without a `body` yields a
`missing_body` diagnostic and no blocks.

Build and run it with Rust 1.99 or newer:

```sh
cargo run -p mls-cli --bin mls -- notes.tm
```

Parsing is read-only by default. Persist generated IDs only when desired:

```sh
cargo run -p mls-cli --bin mls -- --write-ids notes.tm
```

IDs generated by a read-only run are transient. ID writes wrap recognized source
blocks with TeXmacs `with` metadata, preserve all original bytes, and replace the
file atomically after a successful parse.
Malformed tags are errors; duplicate IDs/labels and unresolved references are
reported in the JSON diagnostics array. `--write-ids` refuses invalid or duplicate
ID metadata and symbolic-link targets rather than replacing ambiguous files.
Legacy non-UTF-8 document bytes remain
lossless, although labels and references must be UTF-8 to participate in linking.

Run formatting, lint, unit, property, and CLI integration checks with:

```sh
make test
```

M2 adds `mls-sir`, which provides validated statement schemas, semantic
hashes, and field diffs. `mls-models` provides configured OpenRouter generation
and typed Jev decisions, auditable recordings, and strict offline replay. Model
IDs and request limits live in `config/models.json`. Tests use synthetic fixtures
and loopback transport mocks by default; they make no provider calls.

An explicit live smoke test makes one small generation request and one decisions
request using an existing `OPENROUTER_API_KEY` environment variable:

```sh
MLS_LIVE=1 cargo test -p mls-models live_openrouter_smoke_explicitly_gated -- --nocapture
```

Sanitized call records are stored under ignored `.mls/log/live-smoke/` directories.
Missing cost or confidence remains unknown; it is never silently treated as zero
or certainty. Progress and executed evidence are tracked in
[docs/progress.md](docs/progress.md) and [docs/validation.md](docs/validation.md).

The local Lean integration currently targets Apple Silicon macOS. Install the
pinned Lean 4.19.0, Mathlib and community REPL under ignored repository-local
directories, then run the real integration suite:

```sh
make setup-lean
make test-lean
```

Setup downloads the official Lean archive and Mathlib's compiled cache; it does
not change shell startup files. The launcher uses the pinned REPL through Lean's
interpreter because this host rejects its natively linked executable. The REPL
remains one persistent process with Mathlib imported once. Other platforms need
a corresponding runtime installation path; they are not supported by this setup
script yet.

`mls-lean` exposes candidate environments that callers must explicitly accept
after structural checks. Its generated-source admission grammar is deliberately
restricted; unsupported syntax is an error. Shadow sections use validated module
names and dependency order. If interleaved dependencies create a cycle between
whole sections, generation rejects it rather than emitting invalid Lean imports.

## Batch statement formalization (M2)

`mls batch` asks the generation model for one combined SIR and Lean result for
every definition and theorem-family block, elaborates the Lean statement with a
`sorry` placeholder in the pinned Lean worker, and compares the trusted
extracted structure with the returned SIR:

```sh
cargo build -p mls-cli
target/debug/mls batch notes.tm --replay RECORDINGS_DIR --output report.json
MLS_LIVE=1 target/debug/mls batch notes.tm --live --output report.json
```

Exactly one of `--replay DIR` (offline, strict request matching) or `--live` is
required. Live calls also require `MLS_LIVE=1` and `OPENROUTER_API_KEY`, and
are recorded under `<document dir>/.mls/log/batch-<UUID>/`, the path printed to
stderr. The command writes a document-adjacent pinned Lake project with one
generated `Shadow/<Module>/SectionN.lean` per section, where `<Module>` is
derived from the document file name (`lake build Shadow` compiles it)
and only touches files it owns. Batch results are unconfirmed drafts: statuses
are `not_formalized` (no usable SIR), `sir_drafted` or `formalization_error`
(an SIR without an accepted Lean statement); only the M3 review flow can
produce `statement_confirmed`, and nothing is reported as verified. Each structure check is `matched`, `mismatch` or `unchecked`, and
semantic content (types, hypothesis and conclusion text) is always unchecked in
M2. `--max-attempts N` bounds Lean repairs per statement (default 3).

The evaluation corpus and runner live in `evals/`; see
[evals/README.md](evals/README.md) and the results in
[docs/evals.md](docs/evals.md):

```sh
python3 evals/run.py --replay RECORDINGS_DIR
MLS_LIVE=1 python3 evals/run.py --live --max-attempts 2
```

`make test` runs the offline suites (including the evaluator tests);
`make test-lean` additionally runs the real-Lean worker, pipeline, batch,
proof-core and production-daemon acceptance tests. Real-Lean tests skip
themselves unless `MLS_LEAN_TESTS=1`, which `make test-lean` sets.

## TeXmacs review (M3)

The thin TeXmacs plugin in `texmacs-plugin/mls` drives the engine's review
commands (`mls review-run`, `review-action`, `review-status`; see
[docs/protocol.md](docs/protocol.md)). It saves the document, runs a batch
formalization, and shows an auxiliary "MLS status" panel with one row per block
(status, tooltip message, go-to and review actions) plus a footer badge. A
review card shows the SIR, structure checks and Lean statement, with Confirm,
Reject and Edit. Human decisions are stored next to the document in
`.mls/review/`; a statement becomes `statement_confirmed` only when a reviewer
confirmed (or edited) that exact SIR, its Lean statement was accepted, and all
its dependencies are confirmed. Block identity follows the TeXmacs tree, so a
TeXmacs re-save that only changes layout keeps confirmations and needs no
model call. The plugin writes nothing into the document except the identity
metadata added by `mls --write-ids`.

Install for your own TeXmacs (not done automatically):

```sh
cargo build -p mls-cli
ln -s "$PWD/texmacs-plugin/mls" ~/.TeXmacs/plugins/mls
```

Set the `MLS_BIN` environment variable or the plugin's engine preference to
`target/debug/mls` when TeXmacs is started from Finder. Replay runs need a
recordings directory; live runs need the "Allow live model calls" menu toggle,
`OPENROUTER_API_KEY` and `MLS_LIVE=1` in TeXmacs' environment.

`make test-texmacs` runs the headless plugin suite against a stub engine and
the real `review-status`; `MLS_LEAN_TESTS=1 make test-texmacs` adds the real
end-to-end review flow with replayed model calls and real Lean.
`MLS_TEXMACS_TESTS=1 cargo test -p mls-tm --test texmacs_roundtrip` checks that
real TeXmacs saves leave block identities and canonical text unchanged.

## Live daemon and proof workflow (M4/M5)

The `mls serve` command runs a persistent JSON-RPC session for one saved
TeXmacs document. Its Scheme client sends document snapshots and cursor/review
actions, then renders formalization and proof statuses in the MLS panel. A
confirmation queues a proof-only job for that exact accepted SIR and Lean
statement; the statement remains visible while bounded proof attempts run.
Proof status is separate from statement status: `verified` requires a complete
Lean-checked theorem with no `sorryAx` or disallowed axiom, while exhausted
search is `unproven`. `refuted` is reserved for separately checked positive
Lean evidence; the current proof search does not discover refutations.

Run the local build and replay-backed acceptance checks with the pinned Lean
runtime already installed:

```sh
cargo build -p mls-cli
MLS_LEAN_TESTS=1 cargo test -p mls-cli --test serve acceptance::real_daemon_drafts_confirms_proves_persists_and_reopens_a_saved_document -- --exact --nocapture
MLS_LEAN_TESTS=1 cargo test -p mls-engine --test proof confirmed_statement_reaches_verified_status_with_real_lean_when_enabled -- --exact --nocapture
make test-texmacs
```

With `MLS_LEAN_TESTS=1`, the production-daemon acceptance test uses recorded
model calls and real Lean to check draft, confirmation, proof verification,
persistence and reopen. The pinned Lean proof test checks a real compiled
proof. `make test-texmacs` includes the headless live
client test against a deterministic stub daemon; it checks display of all three
proof labels, but does not obtain those outcomes from live proof search. For
the complete offline and Lean suites, run `make test` and `make test-lean`.

For direct daemon use, start a replay session with
`target/debug/mls serve --replay crates/mls-cli/tests/serve/fixtures/acceptance`
or an explicitly opted-in live session with
`MLS_LIVE=1 target/debug/mls serve --live` (with `OPENROUTER_API_KEY` set).
Send the newline-delimited JSON-RPC messages in [docs/protocol.md](docs/protocol.md)
to stdin; the first `didOpen` must include the complete source of a saved
document. The replay acceptance test above provides the complete deterministic
request sequence, including confirmation and proof completion.

To try the live TeXmacs client manually, build MLS and install the plugin as
shown above, then start TeXmacs with `OPENROUTER_API_KEY` available and
`MLS_BIN` set to the built `target/debug/mls`. Open a saved `.tm` file, enable
“Allow live model calls”, start the MLS live session, and choose “Open live
status panel”. Review a drafted SIR to confirm it; the panel keeps its accepted statement visible while proof
search runs and then shows `verified` or `unproven`. A proof search failure is
not a refutation. Live calls require network access and are recorded beside the
document. See [docs/protocol.md](docs/protocol.md) for JSON-RPC messages and
serialized view fields, [docs/progress.md](docs/progress.md) for remaining
acceptance work, and [docs/validation.md](docs/validation.md) for the boundary
between recorded evidence and checks still to run. New untagged prose typed
mid-session is picked up after save and live-session restart so its startup ID
can be persisted. The manual GUI pass remains owner-owed and unverified; it
covers the menu, rendered colors, tooltips and review dialog.
